# E2E test cases: next phase (assessment and design, 2026-10-13)

Status: proposal. Companion to `design.md` (phase 1 spec), ADR 0002 and `STATUS.md`.
Author: Nam Do with Claude. Sources: the three `tester-army` repositories, `e2e.tester.army/docs`,
`docs.tester.army`, `docs.stagehand.dev`, and the code under `packages/e2e-runner`, `packages/shared`,
`apps/backend`, `apps/evidence-web`, `packages/ui`.

## 0. Summary

1. We already run on Tester Army `e2e`. The useful move is to upgrade it (0.16.0 to 0.20.0), not to
   add another framework. `scout` is worth copying for the API grammar. `cli` and Stagehand add
   nothing we need.
2. "API only" replay is a new, separate cache layer beside the existing UI action cache. It is
   right for preconditions and data setup, wrong as a substitute for UI regression. The design
   below records the request graph per step, correlates values between responses and later
   requests, and replays under the same replayed / handed off / missed semantics QA already know.
3. Chaining stays on `[Use: KEY]`, which exists, plus a `mode=` argument, declared `Outputs:`,
   and session reuse through e2e `test.setup` sessions (the equivalent of Tester Army's
   Preparation Test).
4. The UI gets one entry point ("What do you want to test?"), a case page instead of a sheet,
   one click from list to the latest run, and a run view with two focal points.
5. Regression speed comes from four things: a deterministic assert cache (promised in `design.md`
   §4 and never built), one e2e process per suite with saved sessions, strict cache in CI, and
   skipping preconditions whose data already exists.
6. Postgres steps follow the `[Query: PROFILE] ... -> {name}` shape with read-only credentials,
   a cached SQL script per step and the same hand-off behaviour.

Features already in 0.16 that we do not use yet:

- `test.setup(..., { sessions: [...] })` and `session.save(name)`. A named session (cookies,
  local storage, IndexedDB) restored by other tests. This is the Preparation Test from
  `docs.tester.army/run/prep-test` and it is exactly what multi-case regression needs.
- `test.extend` fixtures and `fetch` with `browser.cookies()` for signed-in API calls
  (`docs/api-testing`). This is the officially supported way to do API steps inside an e2e run.
- `defineTool(..., { mutates })` project tools. Read-only tools cost no action slot and do not
  break replay; mutating tools leave a "gap" the agent fills live. A database lookup fits the
  read-only shape.
- `e2e mcp` with the `locate` tool, which returns the `screen.*` call when exactly one element
  matches. That is how the authoring agent can turn a judged assert into a deterministic locator.
- `expect(...).toMatchSchema(zodSchema)` for API responses.

Verdict: upgrade first. Everything in sections 2, 4 and 5 is cheaper on 0.19+ because the
engine context, the cache report fields and sessions are already there.

### 1.4 Tester Army hosted product (`docs.tester.army`)

Concepts we should copy, in priority order:

Still not a candidate for the core. The v4 cache is server-side on Browserbase and does nothing

## 2. API replay, run modes and chaining

### 2.1 What "API only" can and cannot prove

Replaying the HTTP requests a UI flow made exercises the backend path the UI would hit, with the
real payload shapes and ordering. It proves backend logic and produces real data. It does not
prove the UI: a broken button, a hidden field, a wrong label all pass. So the mode is for
preconditions and for "is the backend still accepting this flow", never for the case under
test. The UI below makes that distinction visible rather than hiding it behind a dropdown.

Known failure classes an API replay must handle, with the LittleLives specifics:

- Identity: cookies, bearer tokens in `Authorization`, `X-Dev-Domain` tenant headers. Values
  change per session.
- Correlation: an id returned by request 3 appears in the path or body of request 7.
- Volatility: timestamps, nonces, `updated_at`, request ids.
- Idempotency: replaying a `POST` creates another record. UAT already suffered from fixture
  growth (regression on 2026-10-11 created about 1,180 students). Replays need dedupe and
  cleanup, not just speed.
- Reads: `GET` calls are mostly noise for setup but useful as checks.

### 2.2 Recording

The engine wrapper (`runtime/engine.ts`) attaches Playwright `page.on('request')` and
`page.on('response')` listeners per attempt and writes `requests.jsonl` beside `steps.jsonl`.
Each record: step id (from the step log window), sequence, method, URL, resource type, request
headers and body, response status, headers and body (text up to 64 KiB, as the archive does
today), timing. This replaces the `trace.zip` dependency for network in the archive and feeds the
API script builder. Secrets go through the existing redaction ledger; passwords never reach disk
in plain text (the login request body stores `{{secret:PCF.password}}`).

Filter to "API" requests: same-origin or allow-listed origins from the environment
(`test_environments.api_origins_json`, new), resource type `xhr` or `fetch`, non-2xx included.
Static assets, analytics and third-party calls are dropped from the script but stay in evidence.

### 2.3 Building an API script from a passed step

After a step passes (same trigger e2e uses for the UI cache: a later verification passed), the
runner builds one `api-requests` script per step:

1. Order the step's API requests. Classify each as `mutation` (non-GET, or GET to an endpoint the
   environment marks as mutating) or `read`.
2. Correlate. For every token in a request (path segments, query values, JSON leaf values,
   header values) that looks dynamic (UUID, numeric id, JWT, ISO date), search earlier responses
   in the same run for the same value. A hit becomes a capture binding
   `{ from: requestSeq, path: "data.application.id", as: "v1" }` and the later request uses
   `{{v1}}`. No hit and matches a run param or extracted variable: bind to that. No hit at all
   and looks like time: mark `volatile`, regenerate at replay. No hit and unknown: keep literal,
   flag the script `review` so the UI shows it.
3. Auth: headers named `authorization`, `cookie`, `x-dev-domain` and any header the environment
   lists become `{{auth.<name>}}`, resolved at replay from the live browser session (section 2.4).
4. Expectations per mutation: status class (2xx), and a response shape inferred from the recorded
   body (keys and JSON types, two levels deep). Optional: validate against sv-backend's OpenAPI
   when the environment has `openapi_url`.
5. Store as `test_step_scripts` row with new column `kind = 'api-requests'`, `requests_json`,
   same `status`, `verified_count`, `stale_reason` columns as UI scripts. Reads are kept in the
   script but flagged `check: false` by default.

The correlation step is the part that decides whether this works. Load-testing tools call it
"correlation" and it fails on values that are transformed (base64, hashed, prefixed). The
`review` flag plus the UI (section 3.4) is how QA fixes those by hand: pick the source field.

### 2.4 Replay

A step in API mode compiles to `await jl.replayApi(stepId, scriptRef)` in the generated test
file instead of `agent.act(...)`. The helper:

1. Resolves `{{auth.*}}` from `browser.cookies()` and from local storage keys the environment
   lists (`auth_storage_keys_json`, for bearer tokens kept in `localStorage`). This requires a
   signed-in browser context, which the Login macro or a saved session provides. A pure API login
   is a later option (replay the recorded login request with the credential handle).
2. Executes requests in order through `fetch` (the pattern from `docs/api-testing`), applies
   captures, substitutes `{{...}}`, regenerates volatile values.
3. Checks each mutation's expectations. A failed check ends the API replay and hands off: the
   remaining step runs in UI mode (agent, or UI replay if a UI script exists). The report records
   `mode: api-replayed | api-handoff | replayed | handoff | agent` per step, so the existing step
   list, cost column and Scripts tab keep working with one more mode value.
4. Marks the API script `stale` on hand-off, exactly as `updateStepScripts` does for UI scripts.
5. Idempotency: before running a mutation sequence whose first request matches a recent run's in
   the same environment within the dedupe window, offer the previous outputs instead
   (section 2.6). Every replayed mutation is logged to `test_run_steps.requests_json` so the run
   page can list what a run created. No cleanup job (decision 5 in section 8): replayed data stays,
   the reuse window keeps the volume down.

Access (decision 2): anyone who can run a case can run it in API mode, on any environment. The
only gate is configuration: an environment without `api_origins_json` refuses API mode with the
blocked reason `API_NOT_CONFIGURED`, and the run dialog greys the option out with that text.
Policy per environment, copied from scout: `allowed_paths`, `max_requests_per_step` (default 50),
rate limit.

### 2.5 Run modes

Three values on `test_runs.execution_mode`:

| Mode | Case's own steps | `[Use]` blocks | When |
| --- | --- | --- | --- |
| `full` (default) | UI (cache, then agent) | UI | Regression of the case itself |
| `hybrid` | UI | API script if active, else UI | Default when the case has `[Use]` preconditions and API scripts exist |
| `api` | API script, hand off to UI on failure | API | Data setup, backend smoke, "does this flow still accept input" |

The run dialog shows these as "Full", "Fast preconditions" and "API only (does not test the
UI)". A step-level override exists in the transcript: `[Use: TC-0012, mode=api]`.

### 2.6 Chaining and outputs

`[Use: KEY, p=v]` already runs another case inline, nested up to four levels. Three additions:

1. `Outputs: applicationId, studentId` metadata line on the used case. An output is a variable
   the case sets through `[Extract: name]` or through an API capture or a `[Query]` binding.
   Outputs are persisted to `test_run_steps.outputs_json` and to the run's `params_json` so they
   survive the process and show in the run page.
2. Outputs flow to the parent as `{registration.applicationId}` where `registration` is an
   alias: `[Use: TC-0012 as registration, mode=api]`. Dotted variable references need
   `extractStepReferences` to accept `{alias.name}` the way `{cred:P.field}` already does.
3. `Reuse:` policy on the used case: `never` (default), `within 30m`, `while <query>`. With a
   reuse window, a `[Use]` block first looks for a finished run of the same case, same environment,
   same params inside the window, and takes its outputs without running anything. The run page
   shows "preconditions reused from run X". This is what makes "re-run with many preconditions"
   fast on the second attempt, and it is where the `[Query]` step (section 5) can confirm the
   data is still in the expected state before reuse.

Scenario paths as a first-class object (graph of cases) are not needed for the example in the
brief: "submit registration (API) then approve (UI)" is a case with one `[Use]` block. A
`test_scenarios` table can come later if QA start drawing graphs; the output contract above is
what it would build on.

### 2.7 Sessions (Preparation Test)

Generate `tests/auth.setup.e2e.ts` per credential profile the run needs, with
`test.setup(..., { sessions: ['PCF_HQ'] })` running the Login macro once and `session.save`.
Every case test in the same e2e process declares `{ session: 'PCF_HQ' }`. Within one process,
login happens once per profile instead of once per case. Sessions last one run by e2e design, so
the saving comes from running a suite as one process (section 4.2), not from caching across runs.

### 2.8 Implemented (phase D, 2026-10-13)

What landed differs from the text above in these points; everything else is as written.

- Reads stay in the script with `check: false` and are replayed (the app's own reads may be
  needed for captures); only mutations are checked. An environment may not yet mark a GET as
  mutating.
- Correlation searches the nearest earlier response first, within the step and then in earlier
  steps. A value found in an earlier step's script becomes a capture with `fromStepId`; at replay
  it resolves only when that step replayed its script in the same run, otherwise the step hands
  off. A value found in a step without a script, or nowhere, is flagged `review` with the step's
  earlier response fields as candidates; the fix is `PATCH /test-cases/:id/scripts/:scriptId`.
- Bearer tokens: `auth_storage_keys_json` is not a column (decision 1); `apiPolicy.authStorageKeys`
  carries the localStorage keys when a case needs them, and the `authorization` header is left out
  otherwise. `set-cookie` headers of replayed responses are added to the browser context.
- The case's own `open` steps always navigate the browser (their traffic is a document load, not
  API). Only `act` steps replay; asserts, waits and extracts stay judged, also under `api`.
- A passed `act` inside a `[Use]` block records a script on any run (full included), so the
  first full run of the parent prepares the hybrid run. The case's own acts record only under
  `api`.
- The reuse lookup hashes the `[Use]` block's explicit arguments the way the backend hashes a
  run's request params, so a hit needs a standalone run of the used case requested with those
  params on the same environment. Daemon runs look up through the run token; local CLI runs do
  not (`--no-reuse` exists for symmetry).
- `openapi_url` is stored and handed to the runner but not validated against yet.
- Step-level outputs and the run's merged `outputs` are on the run detail; the run's
  `params_json` is not rewritten.

## 3. UI

### 3.1 What the audit found

- Creating a case: two dialog steps, title is the only enforced field, the case is created active
  with zero steps allowed. Plain-language input exists only under Import, General instructions,
  which needs a runner, a batch page, a commit and the review queue (four screens).
- Reaching the latest run: row click, "Test sessions" tab, run link, then expand the collapsed
  evidence stream. Three clicks and a route change before the recording and steps are both
  visible; the "Last outcome" badge is not a link.
- The case sheet stacks eleven things in one scroll (metadata strip, Needs row, six stats, footer
  line, tab bar, seven-field form, editor toolbar, rows, ten-item shortcut footer).
- Lint shows in four places, cache status in four, last outcome in three.
- Review queue and import use a monospace read-only `TranscriptView`; macros use a bare textarea;
  the case uses the structured editor. Three editors for one grammar.
- No charting or diagram library in any `package.json`.

### 3.2 Entry: "What do you want to test?"

One dialog from the "New" button, the `c` key and the empty state. It opens on a plain-text box:

```
Describe the test in your own words
┌──────────────────────────────────────────────────────────┐
│ Login as PCF HQ admin, open the registration list, open   │
│ the first pending application and approve it. The status  │
│ should change to Approved and the parent gets an email.   │
└──────────────────────────────────────────────────────────┘
Environment  [pcf-uat ▾]        Start from  [TC-0012 Submit registration ▾ optional]

[ Write steps myself ]                               [ Run it with AI → ]
```

Defaults: last used environment, no tags, no title (the AI proposes one). "Run it with AI" does
this, in one screen:

1. The act model drafts a transcript from the text, agent notes, environment variables and the
   three most similar cases (`find_similar_test_cases` exists). Draft shown on the left as the
   structured step list, editable.
2. The draft runs immediately in `read-write` cache mode on the environment's pool with live
   view on the right. The user can take over (exists). Every Act that passes records a UI script
   on the spot, so the first regression run is already a replay.
3. For each judged Assert that passes, the runner asks the model for a locator check through the
   `locate` vocabulary (section 4.1) and stores it with the step.
4. On finish: "Save as TC-0071" with the proposed title. Status `active` when a person watched
   the run; MCP-created cases keep going to the review queue. Tags, links, description and params
   live in a side panel labelled "Details (optional)" and can be filled later.

The existing exploration machinery (`test-explorations.ts`) stays for bulk import and Jira. The
new path is a single run with `source: 'ai'` and `trigger: 'author'`.

"Write steps myself" opens the same case page in edit mode with the structured editor.

### 3.3 Structured editor redesign (smart text mode)

Keep `packages/ui/step-editor` as the engine; change its presentation:

- Checkpoints become section headers that span the width, with their own status chip.
- Each step is one row at 44 to 52px height: a 6px colored rail for type (Act green, Assert blue,
  Open grey, Login amber, Use purple, Query teal, API orange), the instruction as the only large
  text, chips for variables and credentials inline, and a trailing status cell (cached, stale,
  last outcome) that only shows when non-empty.
- The type word moves into the rail tooltip and the `/` picker. Low-tech QA should read the
  instruction, not the tag.
- Lint moves to the row's right edge as one dot; messages appear on hover or focus. The summary
  line stays, the footer cheat sheet moves behind a `?` button.
- Text mode stays as the escape hatch.
- The same component renders read-only for review, import and macros. One grammar, one editor.

Target width: the full page, not a 1000px sheet. Target reading test: a QA who has never seen
the grammar can say what the test does from the instruction column alone.

### 3.4 Case page and flow view

> Revised 2026-10-13 after review: the left pane is Flow | Steps | Text (Flow by default), the
> right pane always shows one run behind a run picker; the runs table moved into the Details
> drawer. §3.3's colour rail became a verb column. §3.5's pill rail became a step column under a

Replace the sheet with a route, `/test-cases/:id`. Layout: a header line (key, title, status,
Run, `⋯` menu), then two panes.

Left pane, "Steps": the editor above. Right pane, one of three views chosen by a segmented
control, defaulting by state:

- "Latest run" (default when runs exist): the run view from section 3.5 embedded, for the newest
  run. Steps on the left highlight as the video plays; the editor is read-only while a run is
  selected and editable when the user clicks "Edit steps".
- "Flow" (default for cases with `[Use]`, `[Query]` or `[API]` steps): a flow diagram built on
  `@xyflow/react` from the start (decision 4). Layout is computed, not dragged: `dagre` or
  `elkjs` top-to-bottom, nodes locked, panning and zoom on. Node types:
  - `checkpoint`: title, the steps inside as a compact list, outcome dot, cache ratio
    ("4/5 replayed").
  - `use`: the linked case key and title, mode chip (API, UI, reused), a "open TC-0012" link.
  - `query` and `api`: profile name, the instruction, row count or request count from the latest
    run.
  - `output`: small pill nodes on edges, `applicationId`, hover shows the last value.
  Edges carry outputs and are animated only while a run is in progress (`animated` on the edge
  the runner is currently inside). Click a node to select it: the editor scrolls to the matching
  rows, the run view seeks to the step. Selection, not hover, drives everything, so keyboard users
  get the same result through `j`/`k` on the editor.
  Custom nodes are plain divs styled with the Tailwind tokens; `@xyflow/react` ships its own base
  stylesheet, import it once in `index.css` under `layer(vendor)` so the legacy layer cannot
  override it.
- "Runs": the sessions table, with filters, where it is today.

The `⋯` menu takes rename, tags, links, duplicate, archive, versions (with a real diff view),
export, clear scripts. The Scripts tab becomes a per-step drawer inside the editor row: click the
"cached" chip to see the rendered Playwright, the API request list or the SQL, and to fix a
correlation flagged `review`.

### 3.7 Interaction and motion

The web app already has the right base: `--ease-out: cubic-bezier(0.23, 1, 0.32, 1)`,
`.jl-tc-press` with `scale(0.97)` on `:active`, `@starting-style` fades and a reduced-motion
block in `index.css`. The rules below extend that to the new screens. The first question for every
animation is how often a QA sees it in a day; the answer decides whether it animates at all.

| Interaction | Frequency | Decision |
| --- | --- | --- |
| `j`/`k`, `n`/`p`, Enter, Esc, `/`, `c`, `r` | 100+ per day | No animation. Selection and route changes from the keyboard are instant. The step rail highlight moves without transition when triggered by a key. |
| Row hover, chip hover, button hover | tens per day | Colour only, 120ms, gated behind `@media (hover: hover) and (pointer: fine)`. |
| Press on any button, row, rail step, flow node | tens per day | `scale(0.97)`, 160ms `--ease-out`. Already `.jl-tc-press`; apply it to the rail and to flow nodes. |
| Details drawer open and close | a few per run | `transform: translateX` + opacity, 220ms in, 160ms out, `--ease-out`. Never `width`; the drawer slides over the video, the video does not reflow. |
| "What do you want to test?" dialog | a few per day | Scale from 0.96 and opacity, 180ms `--ease-out`, `transform-origin: center` (modal). Exit 120ms. |
| Draft steps appearing during an authoring run | rare | Stagger 40ms per row, translateY(6px) to 0, opacity, 240ms. The one place delight is allowed; interaction is never blocked by it. |
| Step status change (running to passed or failed) | per step, while watching | Colour transition 200ms `ease`; the failed step gets one 300ms scale pulse to 1.02 and back, nothing repeating. |
| Live frame refresh (every 1s) | constant | Crossfade 150ms with `filter: blur(2px)` on the outgoing frame so two frames never read as two objects. `will-change: opacity` on the two layers only. |
| Seek bar step segments | constant | No animation on the playhead; it follows `timeupdate`. Hover on a segment shows the instruction in a tooltip with the 125ms scale from `var(--transform-origin)`, instant for the next segment while one tooltip is open. |
| Flow nodes on run progress | per step | Border colour 200ms; the active edge uses xyflow's `animated` dashes; no node movement, layout is fixed per transcript version. |
| Toasts (queued, saved, repair queued) | a few per day | Keep the existing toast layer; enter from the same edge it exits to. |
| List virtual rows, filters, column changes | tens per day | No animation. `data-instant` already disables row transitions; keep it for every list mutation. |

Other rules for the new screens:

- Only `transform`, `opacity`, `clip-path` and colour transition. Panels never animate `width` or
  `height`; the run view's video keeps its box while the drawer slides over it.
- The "cached" and "stale" chips in the editor row use a `clip-path: inset()` fill from left to
  right over 2s linear while a repair run is replaying that step, snapping back in 200ms
  `--ease-out` on completion. It reads as progress without a spinner.
- Spinners spin fast (0.8s per turn). The queue position counts down in place, no fade.
- Hold-to-confirm for "Clear all scripts" and "Cancel run": 1.2s linear `clip-path` fill on the
  button, 200ms release. These are rare and destructive, so the slow press is deliberate.
- `prefers-reduced-motion`: keep colour and opacity transitions, drop all translate, scale and
  stagger. The existing media block in `index.css` covers `.jl-tc-*`; new classes join it.
- Run every new transition at 5x slow motion in DevTools before merging; check that
  colour, opacity and transform reach their end state together.

## 4. Regression speed

### 4.1 Deterministic assert cache

`design.md` §4 promised that asserts cache a deterministic check; `report/build.ts:122-124` marks
every non-act step `not-cacheable`, so every regression run pays a judge call per Assert.

Build it as the UI script's sibling: after a judged assert passes, ask the act model one more
question with the current screen snapshot: "which single locator proves this?" The runner
validates the answer with e2e's `locate` logic (exactly one match) and stores
`{ locator: { role, name } | { testId } | { text }, matcher: 'visible' | 'text' | 'url', value }`
as a `test_step_scripts` row with `kind = 'assert-check'`. On replay the step compiles to
`try { await expect(screen.getBy...).toBeVisible() } catch { await agent.assert(...) }`. A fallback
marks the check stale. Asserts that need judgement (counts, "looks right") get no check and
stay on the judge; the model may answer "none".

Expected effect on the spike numbers in `design.md` §14: run 2 made 6 judge calls for 39s. With
checks, a fully cached run makes 0 model calls, and the remaining time is browser time.

### 4.2 One e2e process per suite

Today one run is one `e2e run` process with one test and `workers: 1`. For a suite batch, generate
one project with one test file per case and the setup test per credential profile (section 2.7).
Gains: one Chromium launch, one login per profile, e2e's own `workers` for parallel cases on a
pool with `max_concurrent_runs > 1`, and `{ serial: true }` groups when cases share data (the
Sequential mode from Tester Army, with "a failure cancels the rest").

The batch still produces one `test_runs` row per case; `report.json` has per-test results and the
step log already carries step ids. Evidence: one recording per test (e2e records per attempt),
so per-run evidence stays.

### 4.3 Strict cache for regression

Regression runs default to `cache_mode = strict`. A stale script fails the step with
`REPLAY_STALE` and makes no model call. The finalizer queues one repair run in `read-write`
for that case, tagged `trigger: repair`, so the regression report stays cheap and deterministic
and the fix happens once, off the critical path. The run page shows "stale, repair queued".

### 4.4 Skip preconditions whose data exists

Section 2.6's `Reuse:` window plus a `[Query]` guard (section 5) lets a `[Use]` block resolve to
existing data: "a pending application for student X created in the last 30 minutes" found by SQL
means the registration flow does not run at all. The run reports `preconditions: reused (query)`.

### 4.5 Smaller items

- `JL_SETTLE_MS` retry only when the page had pending network in the last second (we will have
  the request log), not always.
- `evidence_policy` per run: `full` (video on) for authoring and failures, `light` (video
  `retain-on-failure`, screenshots per step) for scheduled regression. Evidence stays the
  default; this is an opt-in for large nightly suites.
- Pool `max_concurrent_runs` default 1 is the real ceiling on wall time. Document the sizing rule:
  one Chromium per 2 vCPU and 2 GB.

## 5. Postgres and other integrations

### 5.1 Grammar

```
[Query: pcf-uat-db] a K1 student with a pending registration and no holds -> {student}
[Open] /student-detail/{student.id}
[Assert] the page shows {student.name}
...
[Query: pcf-uat-db] the application {registration.applicationId} has status APPROVED
```

- `[Query: PROFILE] text -> {name}` binds the first row (object) to `name`; `{name.column}`
  references work through the dotted-reference change from section 2.6. `-> {rows}` with a plural
  hint binds the array for datasets.
- `[Query: PROFILE] text` without a binding is a check: it passes when the query returns at
  least one row. This is the database-level assert for data not visible in the UI (the second
  half of the brief).
- `PROFILE` is a `test_credentials` row with `kind = 'postgres'`, fields `host`, `port`,
  `database`, `user`, `password` (secret), `ssl`, `schema_allowlist`, environment-scoped.
- The same shape later covers `[API: PROFILE] text -> {x}` for ad-hoc HTTP calls and
  `[Mongo: PROFILE]`.

> Implemented 2026-10-13 (`wave2/e-postgres`): the grammar executes end to end; `{student.id}`
> resolves at run time from the bound row; a `[Query]` without a binding fails on zero rows.
> `ssl` accepts `true|false|require|disable|prefer|verify-full`; `schema_allowlist` is one
> comma-separated field, edited as chips.

### 5.2 Execution

Three tiers, cheapest first, like the UI cache:

1. Cached SQL script. `test_step_scripts` row with `kind = 'sql'`, `sql`, `params` (placeholders
   bound to run variables), `binding`. Replay runs it directly. Zero rows for a `-> {name}` step is
   a hand-off, not a failure.
2. Agent-written SQL. The act model gets the instruction, the allowed tables with columns and
   types (the same `describe` output the postgre MCP produces, cached per profile per day) and
   up to three example rows per table it asks about. It must return one `SELECT` or `WITH`
   statement. The runner parses it: single statement, no `;`, no DML or DDL keywords, tables inside
   the allowlist, adds `LIMIT 50` and a statement timeout of 10s, runs it on a read-only role.
   The model sees at most 20 rows of results, redacted by column name (`*email*`, `*phone*`,
   `*password*`).
3. Named queries. `test_queries` rows (name, profile, SQL, params), usable as
   `[Query: pcf-uat-db, name=pendingK1Student]` by QA who do not want the model involved.

As an e2e project tool, the same executor is exposed read-only (`mutates: false`) during Act
steps, so an agent that needs "any student id" mid-step can ask. Read-only tools leave no replay
gap.

> Implemented 2026-10-13: `packages/e2e-runner/src/runtime/query.ts` (tiers, cache store,
> agent prompt with Zod-validated `{ sql, rationale, params }`), `pg-describe.ts` (tables,
> columns, types, PK, FK from `information_schema`, cached per profile per attempt), and
> `query-tool.ts` (`lookup_data`, on when the run names postgres profiles, `JL_QUERY_TOOL=0`
> off). Tier order in practice: `name=` → saved query only (no model, no cache); otherwise cached
> script, then agent. Cache endpoints `GET/PUT/DELETE /test-runs/:id/cache/sql/:stepId`
> (`test_step_scripts.kind = 'sql'`); CLI runs use `.e2e/cache/sql/` and `.jl/queries.json`.
> Not sent yet: example rows per table.

### 5.3 Safety

- Read-only database role, enforced on the server, not only by parsing.
- Allowlist of schemas and tables per profile; the describe step shows only those.
- Row cap 50, statement timeout 10s, result size cap 256 KiB.
- Redaction by column name before the model and before evidence. The run page shows the SQL and
  the picked row with the same redaction.
- Runners must reach the database: self-hosted pools inside the VPN (exists). Cloud pools get
  `database: unreachable` as a blocked reason, never a failed outcome.
- Credentials never leave the runner; the backend ships them encrypted per run as it does for
  login profiles.

> Implemented 2026-10-13: the shared guard (`packages/shared/src/sql-guard.ts`) runs in the
> runner before every statement and in the backend before a query is saved; the connection
> itself is `default_transaction_read_only` with the statement timeout and confined
> `search_path`, so parsing is the second line of defence. Blocked reasons `DATABASE_UNREACHABLE`
> and `QUERY_REJECTED`. Redacted columns: `*email*`, `*phone*`, `*password*`, `*passwd*`,
> `*token*`, `*secret*`, `*nric*`, `*ic_number*`, `*mobile*`.

### 5.4 Evidence

A new archive entry kind `integration` with `{ kind: 'sql' | 'http', profile, statement (redacted),
rowCount, sample (redacted), durationMs }`, tagged with the step like actions are. The viewer's
Actions tab lists it; the run view shows it in place of a video segment.

> Implemented 2026-10-13 as archive v5 (`integrationEventSchema`, payload
> `{ kind: "integration", integration: "sql" | "http", … }`, v4 upgraded in memory). The Actions
> tab row shows the profile, row count and duration with the statement in monospace and the
> sample behind a disclosure; the run view overlays the statement and the picked row when a query
> step is selected. Report steps carry mode `query`, `cacheReason` hit/no-entry, `cacheDetail`
> with the SQL and row count, and `outputs` from the binding.

## 8. Decisions (2026-10-13)

Answered by Nam Do on the five open questions of the first draft:

1. Auth transport for API replay: generic cases first. sv-frontend talks to sv-backend with cookie
   credentials (`sv-frontend/src/api/auth-cookie-credentials.ts`, axios `withCredentials`), so
   `browser.cookies()` plus `X-Dev-Domain` is the whole mechanism. The chat client's bearer token
   and any other app-specific need wait until a case asks for them; `auth_storage_keys_json` is
   dropped from the data model until then.
2. API mode has no per-user or per-environment permission. Anyone can run any case in API mode on
   any environment, provided the environment has its API configuration (`api_origins_json`) set
   up beforehand. Missing configuration blocks the run with `API_NOT_CONFIGURED`.
3. An authoring run a person watched saves the case as `active`. Only the MCP and bulk-import
   paths go through the review queue.
4. Flow view uses `@xyflow/react` from the start, with computed layout and custom nodes
   (section 3.4). The interaction and motion rules in section 3.7 apply to it and to every other
   new screen.
5. No cleanup of data created by API replays. The reuse window (section 2.6) and dedupe are the
   only controls on data volume.
