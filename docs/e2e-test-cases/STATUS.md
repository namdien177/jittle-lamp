- 2026-10-13: phase B regression speed (roadmap §4, branch `wave2/b-speed` on the wave2 foundation). (1) **Deterministic assert cache (§4.1).** `runtime/assert-check.ts`: an Assert now compiles to `jl.assertWithCheck(stepId, instructionKey, template, bindings, { agent, screen, browser })` (the generated test imports `test` from `@e2e-dev/web` and takes the `screen` and `browser` fixtures; `jl.fill` still keeps secrets as names). With an active check for the step the runner builds the locator (`{ role, name } | { label } | { text } | { testId }`) and runs the matcher (`visible` → `toBeVisible`, `text` → `toContainText`, `url` → `expect(browser).toHaveURL`) with a 5 s budget: pass = mode `deterministic`, reason `hit`, zero model calls, `cacheDetail` "check expect(screen.getByRole('heading', 'Welcome, HQ admin')).toBeVisible()". A check that no longer holds is marked stale through the store and the judge takes the step over (mode `agent`, reason `action-failed`, detail names the locator); under `strict` the step fails with `REPLAY_STALE` (blocked, now in the runner's blocking codes like e2e's own stale acts) and nothing is judged. Without a check, a read-write run judges as before and then asks the model once (`agent.extract` with a Zod answer schema `{ kind: role|label|text|testId|none, role, name, value, matcher: visible|text|url, expected }`), validates the answer on the live screen (`count() === 1` and the matcher holds within 2 s) and only then writes; `none`, an incomplete answer, an ambiguous locator or an inconclusive model write nothing, and the question is asked at most once per assert per run. Stores: `runtime/cache-store.ts` gains `CheckStore` (`read`/`write`/`stale` by step id) with a file backend (`<cache>/checks/<stepId>.json`, `JL_CACHE_DIR` + `JL_CACHE_MODE` from the runner) and a backend one (`GET/PUT /test-runs/:id/cache/check/:stepId` on the run token; PUT body `{ check, instructionKey, renderedCode }` or `{ stale: true, reason }`; rows are `test_step_scripts` with `kind = 'assert-check'`, `check_json`, `key_hash = check:<stepId>`, versions and status like UI scripts, environment-scoped; writes need read-write, stale marks any mode but off; a backend without the endpoints answers 404 and the runner carries on without checks). Finalisation verifies a `deterministic` assert like a replayed act (`verified_count`), the case stats count checks as cached/stale steps, and the Scripts drawer lists them by their rendered `expect(...)` with no UI change. (2) **Strict regression with repair runs (§4.3).** `trigger` gains `repair` (shared enum + table enum; `test_runs.trigger` has no SQL check constraint, `db:generate` confirms no migration). A suite batch requested without a `cacheMode` now defaults to `strict` (the request schema no longer defaults `cacheMode`; `requestRuns` resolves it per batch kind, everything else stays read-write). When a strict run finishes blocked with `REPLAY_STALE`, `finalizeRun` queues exactly one read-write run (`queueRepairRun`: `trigger: repair`, `retryOfRunId` = the strict run, same case/environment/params/execution mode, priority 10, no batch; no second one while a repair of that case, environment and params is queued or running). Batches ignore repair runs when following retry chains, so the regression verdict stays the strict run's; the run detail carries `repairRunId` (optional) and the run view's Info tab shows "Cache · stale, repair queued". (3) **Batch claim (§4.2, first step).** `POST /runner-pools/claim` takes `{ batchCapacity: n }` (default 1); when the first claimed run belongs to a suite batch, `claimNextRun` is called again with a batch filter (same batch, environment, cache mode, execution mode; same atomic UPDATE and pool ceiling) and the response carries up to n-1 `siblings`, each leased to the worker with its own run token.
